# GAPAGO 메모리 및 비용 관리 전략 정리

> Render 무료 티어(4GB RAM) 환경에서 LangGraph 기반 멀티에이전트 파이프라인을 안정적으로 운영하기 위한 전략

---

## 1. 문제 정의

### 환경 제약
- **서버:** Render 무료 티어, 메모리 한도 4GB
- **런타임:** uvicorn 단일 워커, Python FastAPI
- **ML 모델:** MiniLM 계열 경량 모델 (~80MB)

### 핵심 메모리 위험 요인

| 요인 | 원인 | 위험 수준 |
|------|------|----------|
| MemorySaver 체크포인트 누적 | LangGraph가 8개 노드마다 전체 state를 스냅샷, 세션 종료 후에도 미삭제 | Critical |
| 세션 이벤트 무한 증가 | `_sessions` dict에 SSE 이벤트가 계속 쌓이고, 완료 후에도 pop 안 됨 | Critical |
| PDF 동시 다운로드 스파이크 | 8개 워커가 동시에 arXiv PDF(5~30MB)를 메모리에 로드 → 피크 ~240MB | Critical |
| chat_histories 무한 증가 | 대화 기록 상한 없이 누적 | High |
| HTTP 연결 미정리 | 매 요청마다 새 TCP 연결 생성, GC 전까지 잔존 | Medium |

### 메모리 소비 분석 (개선 전, 최악 시나리오)

```
Python + FastAPI 기본:           ~200MB
ML 모델 (light):                 ~80MB
세션 10개 × events 누적:         ~500MB  (정리 안 됨)
MemorySaver 10개 세션 × 8노드:   ~50MB   (정리 안 됨, 계속 증가)
chat_histories:                  ~100MB  (정리 안 됨)
PDF 동시 다운로드 피크 (8개):     ~240MB  (순간 스파이크)
─────────────────────────────────────────
합계:                            ~1,182MB (시간이 지나면 4GB 초과 → OOM)
```

## 2. 적용 전략

### 전략 1: 세션 생명주기 통합 관리 (Session Lifecycle Management)

**핵심 아이디어:** 세션 생성부터 정리까지 단일 시스템으로 관리하여 메모리 누수 원천 차단

| 구성 요소 | 전략 | 효과 |
|-----------|------|------|
| **세션 자동 정리 (Reaper)** | 백그라운드 태스크가 2분마다 완료/중단/에러 세션을 감지, TTL(5분) 초과 시 자동 삭제 | 무제한 증가 → 활성 세션만 유지 |
| **MemorySaver 체크포인트 해제** | Reaper가 세션 삭제 시 해당 `thread_id`의 LangGraph 체크포인트도 함께 삭제 | ~50MB+ 누적 → ~5MB 안정 |
| **이벤트 수 상한 (500개)** | 세션당 SSE 이벤트 500개 초과 시 오래된 10% 자동 드롭 | 이벤트 메모리 상한 고정 |
| **채팅 기록 상한 (100개)** | 대화 메시지 100개 초과 시 오래된 메시지 잘림 | chat_histories ~5MB 이하 |
| **완료 시점 기록** | 파이프라인 완료/에러/중단 시 `completed_at` 타임스탬프 기록 → Reaper의 TTL 기준점 | 정확한 정리 시점 판단 |

### 전략 2: 실행 시 메모리 스파이크 억제 (Peak Memory Control)

| 구성 요소 | 전략 | 효과 |
|-----------|------|------|
| **PDF 동시 다운로드 워커 축소 (8→3)** | ThreadPoolExecutor max_workers를 8에서 3으로 제한 | 피크 ~240MB → ~90MB |
| **PDF 크기 제한 (10MB)** | 10MB 초과 PDF는 다운로드 생략 | 대형 PDF에 의한 OOM 방지 |
| **결과 저장 스트리밍 직렬화** | `json.dumps()` → `json.dump(f)` (파일 직접 쓰기) | 직렬화 시 메모리 더블링 방지 |

### 전략 3: HTTP 연결 풀링 (Connection Pooling)

| 구성 요소 | 전략 | 효과 |
|-----------|------|------|
| **requests.Session() 공유** | 모듈 레벨에서 단일 HTTP 세션 인스턴스 재사용 | 연결 생성/해제 오버헤드 제거, ~10MB 절감 |
| **Keep-Alive 활용** | TCP 연결 재사용으로 arXiv/Semantic Scholar API 호출 최적화 | 응답 시간 개선 + 메모리 절감 |

### 전략 4: 404 에러 방지 (Session Resilience)

| 구성 요소 | 전략 | 효과 |
|-----------|------|------|
| **서버 재시작 시 interrupted 마킹** | startup에서 running 상태 세션을 interrupted로 전환 | 프론트엔드가 적절한 안내 표시 |
| **stop 요청 시 즉시 삭제 금지** | `_sessions.pop()` 대신 상태만 변경, 정리는 Reaper에 위임 | 스트림 연결 중 404 방지 |
| **프론트엔드 status 사전 확인** | reconnect 전 `/api/status` 호출로 세션 유효성 검증 | 불필요한 404 요청 원천 차단 |
| **SQLite fallback** | 메모리에 없는 세션은 DB에서 상태 조회 → 적절한 안내 SSE 반환 | 404 대신 사용자 친화적 메시지 |

### 전략 5: ML 모델 경량화 (Model Tier)

| 구성 요소 | 전략 | 효과 |
|-----------|------|------|
| **Reranker 경량 모델 사용** | `RERANK_MODELS=light` (MiniLM 계열, ~80MB) | Full 모델 대비 ~200MB 절감 |
| **ONNX GPU 탐색 비활성화** | `ORT_DISABLE_GPU_DEVICE_ENUMERATION=1` 환경변수 | CPU 전용 환경에서 불필요한 리소스 소모 제거 |

## 3. 비용 관련 전략

### LLM API 호출 비용 절감

| 전략 | 적용 위치 | 효과 |
|------|----------|------|
| **경량 모델 우선 사용** | Reranking, 임베딩 등 반복 작업에 경량 모델 사용 | GPU 서버 비용 없이 CPU 환경에서 운영 |
| **PDF Full Text 선택적 다운로드** | 크기 제한(10MB) + 실패 시 abstract fallback | 불필요한 대용량 처리 비용 절감 |
| **세션 자원 적시 해제** | 완료 후 5분 내 메모리 반환 → 서버 스케일업 불필요 | Render 무료 티어 유지 (유료 전환 불필요) |

### 서버 운영 비용

| 항목 | 전략 | 효과 |
|------|------|------|
| **Render 무료 티어 유지** | 메모리 최적화로 4GB 이내 운영 | 월 $0 (유료 티어 $25+/월 회피) |
| **단일 워커 운영** | uvicorn 1 워커로 메모리 최소화 | 다중 워커 대비 메모리 1/N |
| **SQLite 사용** | 별도 DB 서버 없이 파일 기반 세션 저장 | DB 호스팅 비용 $0 |

## 4. 개선 효과 요약

### 메모리 사용량 비교

| 항목 | 개선 전 | 개선 후 | 절감 |
|------|---------|---------|------|
| 세션 데이터 | ~500MB (무제한 증가) | ~50MB (활성 1-2개만) | -90% |
| MemorySaver | ~50MB+ (누적) | ~5MB (완료 시 해제) | -90% |
| Chat histories | ~100MB (무제한) | ~5MB (상한 적용) | -95% |
| PDF 피크 | ~240MB | ~90MB | -63% |
| HTTP 연결 | ~10MB (잔존) | ~2MB (풀링) | -80% |
| **총합** | **~1,182MB (계속 증가)** | **~432MB (안정 상한)** | **-63%** |

### 안정성 지표

```
개선 전: 세션 누적 → 수 시간 내 OOM 크래시, 재시작 시 404 에러
개선 후: 피크 ~520MB, 4GB 대비 87% 여유, OOM/404 원천 차단
```

## 5. 트레이드오프

| 전략 | 트레이드오프 | 판단 근거 |
|------|-------------|----------|
| PDF 워커 8→3 | Full text 로딩 시간 증가 (~2.7배 느림) | 안정성 > 속도. OOM 크래시보다 약간 느린 로딩이 나음 |
| PDF 10MB 제한 | 초대형 논문 full text 누락 가능 | abstract fallback으로 핵심 정보는 확보 |
| 세션 TTL 5분 | 5분 후 과거 세션 메모리 데이터 소실 | SQLite에 결과 영구 저장, 메모리는 활성 세션 전용 |
| 이벤트 500개 상한 | 매우 긴 파이프라인에서 초기 이벤트 드롭 | 실제 파이프라인은 ~200 이벤트 이내 |
| 경량 리랭커 | Full 모델 대비 정확도 약간 하락 | 4GB 환경에서 Full 모델 로드 불가 |
